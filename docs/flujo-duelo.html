Cómo funciona Duelo, de punta a punta

Cada vez que haces un commit o un push en un proyecto vigilado, Duelo recibe ese cambio, lo guarda, lo manda a Temporal para que varios agentes lo revisen en paralelo y te enseña el resultado en la interfaz. Esta página explica cada pieza, deja verlo moverse y dice sin adornos qué existe y qué no.

Las referencias archivo:línea son relativas a backend/src/duelo/ (las del frontend llevan el prefijo frontend/src/) y se comprobaron contra el código de la rama main. El código del hook se cita por función, no por línea, porque se endureció mientras se escribía esta guía (change harden-local-project-hooks).

1 · Visión general

Duelo es un monorepo con un backend Python (FastAPI + Temporal + Postgres) y un frontend React. El backend sigue una arquitectura hexagonal: la lógica no sabe nada de HTTP, de la base de datos ni de Temporal; son los adaptadores los que se conectan por puertos. import-linter impide en CI que una capa interior importe una exterior.

Adaptadores · entrypoints · workflowsFastAPI (entrypoints/api/), SQLAlchemy (adapters/persistence/), cliente de Temporal (adapters/orchestration/), git y gh (adapters/git/, adapters/github/), workflows y activities (workflows/).

Las piezas en una frase

Hook de gitavisa a la API de cada commit/push sin bloquear a git.
API (FastAPI)valida, guarda e idempotentemente arranca la review; también sirve las lecturas.
Postgresfuente de verdad: projects, changes, reviews, events.
Temporalorquesta la review: cola platform (workflows) y cola agents (activities).
Workersun proceso con dos Worker, uno por cola (worker.py:24-39).
Frontendlee la API por HTTP y se refresca solo cada 5 s.
Dato clave: Postgres es la fuente de verdad y Temporal solo orquesta. Por Temporal viajan únicamente identificadores (change_id, agent_name, run); el diff nunca viaja, cada activity lo carga de la base de datos (workflows/activities.py:49-51).

3 · El flujo paso a paso

Esto es lo que recorre un commit desde que lo haces hasta que lo ves en pantalla. Cada paso coincide con uno del simulador.

  1. git commit / git push → hook Al añadir un proyecto local (POST /projects, solo con LOCAL_PROJECTS_ENABLED=true) la API instala los hooks post-commit y pre-push entre los marcadores # >>> duelo >>> / # <<< duelo <<< (adapters/git/hook_installer.py, render_block e install), respetando core.hooksPath y los hooks que ya tuvieras.
    • El hook nunca bloquea a git: hace fork, el padre sale con código 0 y el hijo envía en segundo plano con plazo corto y errores silenciados (entrypoints/hook.py, _detach_and_run y main).
    • post-commit envía el commit recién hecho. pre-push lee de stdin lo que se va a subir y solo envía commits de ramas (refs/heads/): ignora borrados y tags, y manda como mucho 20 commits por referencia, los más antiguos primero (entrypoints/hook.py: MAX_PUSH_COMMITS, pushed_commits).
    • Antes de enviar, el hook trunca el diff a 1 000 000 de caracteres, título a 500, autor a 255 y rama a 255 (build_payload); después la API vuelve a truncar el diff a 200 000 (paso 2).
    • Credenciales: solo del fichero hook.env (modo 0600) cuya ruta va dentro del bloque instalado (--env-file, entre comillas simples); el entorno de quien lanza git no puede cambiar a dónde viaja el token, y la URL debe ser http(s) (entrypoints/hook.py: load_config). El token no vive en el repo. Lo implementa el change harden-local-project-hooks.
    • No hay cola ni reintentos: si la API está caída, ese envío se pierde. Un push posterior solo lo recupera si el commit sigue en el rango que sube (rama, dentro del tope de 20 por referencia); un tag, un commit ya subido o uno más allá del tope no se reenvían.
    • Limitación conocida: el hook usa urllib, que sigue por defecto las redirecciones 301/302/303 (las vuelve GET pero conserva las cabeceras, incluida X-Ingest-Token); 307/308 no se siguen. Si la URL de hook.env redirigiera a otro host, el token viajaría allí. La URL la escribe la API al dar de alta el proyecto, así que no cambia sola.
  2. POST /ingest/commit · /ingest/pr Dos dependencias en este orden (entrypoints/api/routers/ingest.py:20-24): primero el límite de peticiones (entrypoints/api/rate_limit.py:14-28, ventana deslizante en memoria, 300 peticiones/60 s por IP, 429 con Retry-After) y luego el token X-Ingest-Token (entrypoints/api/auth.py:9-18, hmac.compare_digest, 401 si falla). Los intentos con token inválido también gastan cupo.
    • Validación: el esquema pydantic prohíbe campos extra y limita longitudes; el dominio vuelve a comprobar NUL y tamaños (domain/change.py) → 422.
    • El proyecto debe existir (application/ingest_commit.py:49-51) → 404 «Proyecto desconocido».
    • El diff se trunca a max_diff_chars = 200 000 y se marca diff_truncated (application/ingest_commit.py:63-64, config.py:46). Ojo: el cuerpo HTTP se recibe entero antes de truncar.
    • Se calcula diff_summary (archivos, añadidas y borradas) solo para formato git diff (domain/diff.py).
  3. Guardar en Postgres (idempotente) INSERT … ON CONFLICT DO NOTHING RETURNING id sobre la restricción UNIQUE (project_id, kind, head_sha) (adapters/persistence/change_repository.py:26-53). Si el change ya existía, se devuelve la fila existente sin tocarla (:55-62) y no se emite evento. Si es nuevo, se inserta en la misma transacción el evento change.created en events (:64-70). El estado status del change queda siempre en pending; el estado útil es review_status, derivado de las reviews.
  4. Arrancar la review en Temporal TemporalReviewStarter.start (adapters/orchestration/temporal_review_starter.py:22-39) lanza el workflow por nombre, "ReviewCommitWorkflow" (:26), en la cola platform (:31), con id determinista {kind}-{project_id}-{sha} y sufijo -r{run} desde el segundo run (:42-44). La política ALLOW_DUPLICATE_FAILED_ONLY (:34) hace que una review completada no se relance al reenviar el commit y que WorkflowAlreadyStartedError se trate como éxito silencioso (:36-37). Usa el namespace default y el cliente conecta de forma perezosa (adapters/orchestration/temporal_client.py), así que la API arranca aunque Temporal esté caído.
    • Si el arranque falla: ReviewStartError (:38-39) → 503 (entrypoints/api/routers/ingest.py:43-47). El change ya quedó guardado, así que reenviar es seguro.
    • No hay transacción compartida entre Postgres y Temporal: si la API muere justo entre ambos pasos, el change queda pending sin workflow (la UI lo marca stale tras 30 min, pero nada lo recupera solo).
  5. Respuesta 202 {change_id, diff_truncated, created} (entrypoints/api/routers/ingest.py:56-62). created=false indica reingesta idempotente: los campos del segundo envío se ignoran por completo.
  6. Workflows y activities — detallado en la sección Temporal: el padre ReviewCommitWorkflow lanza el hijo ReviewChangeWorkflow, que ejecuta run_review una vez por agente, en paralelo.
  7. Persistir reviews y eventos Cada activity guarda una Review y su evento (review.completed o review.failed) en una única transacción, idempotente por UNIQUE (change_id, agent, run) (adapters/persistence/review_repository.py:22-72, :52). Solo se guardan reviews terminadas: no existe una fila «en curso».
  8. Lectura y UI — ver Lectura y Frontend: la UI pregunta a la API cada 5 s y calcula el estado a partir de las reviews guardadas.

Alta, baja y sincronización de proyectos locales

Solo existe con LOCAL_PROJECTS_ENABLED=true (apagado por defecto: sin él, los tres endpoints dan 404 aunque lleves token). Todos exigen X-Ingest-Token y pasan por el límite de peticiones.

Alta (POST /projects)

  • Ruta estricta: absoluta, sin .., existente, carpeta y no enlace simbólico; debe ser la raíz del repo, no una subcarpeta (adapters/git/local_repository.py:26-47). Si no, 422.
  • Slug: owner/repo del remoto origin, o el nombre de la carpeta. Slug o carpeta repetidos → 409.
  • Primero se guarda, luego se toca el disco; si los hooks no se pueden instalar, el registro se borra (application/local_projects.py:52-72).
  • core.hooksPath fuera del repo se rechaza: un directorio de hooks compartido ejecutaría el bloque en todos los repos (adapters/git/hook_installer.py, _hooks_dir, :158-185).
  • Hooks existentes: deben ser scripts de shell y no enlaces simbólicos, o la instalación falla; el bloque de Duelo va entre marcadores y se añade sin tocar el resto (:188-199).
  • Escritura con vuelta atrás: primero se comprueba todo, luego se escribe el fichero de credenciales y los hooks; si uno falla, los ya escritos se restauran (:112-123). Cada hook se reemplaza de forma atómica (fichero temporal + os.replace).

Baja (DELETE /projects/{slug})

  • Primero se desinstalan los hooks y solo si se logra se borra el proyecto con sus changes, reviews y eventos (application/local_projects.py:75-91).
  • Si los hooks no se pueden quitar: 409 y el proyecto se conserva, para poder reintentar (entrypoints/api/routers/local_projects.py:78-80). Borrar antes dejaría hooks activos con el token y sin registro.
  • Quitar el bloque restaura el hook del usuario tal como estaba; si el hook era solo de Duelo, se elimina el fichero.

Sincronizar PRs (POST /projects/{slug}/sync-prs)

  • Ejecuta gh pr list --state open --limit 30 en la carpeta del repo y luego gh pr diff N por PR (adapters/github/gh_cli.py:9-37): máximo 30 PRs abiertas, timeout de 30 s por llamada a gh y diff truncado a 1 000 000 de caracteres.
  • Una PR malformada se salta; una que rompe los límites del dominio se descarta con un aviso, y no tumban a las demás (adapters/github/gh_cli.py:33-34, application/local_projects.py:107-126). Cada PR se ingesta como kind=pr, idempotente por SHA.
  • gh ausente, sin sesión o sin respuesta → 503 con un mensaje claro.
Sincronización periódica (opcional). Con PR_SYNC_INTERVAL_SECONDS > 0 se ejecuta al arrancar y luego cada intervalo; un fallo se registra en el log y el bucle continúa, y un proyecto que falla no impide los demás (composition.py:227-230, entrypoints/api/background.py:10-23, application/local_projects.py:129-139). Por defecto vale 0 (apagado). Con varios workers de uvicorn cada uno lanzaría el suyo: es inocuo por la idempotencia, pero redundante.

4 · Temporal: workflows, activities y colas

Hay dos workflows y una activity, repartidos en dos colas de tareas. Un solo proceso (python -m duelo.worker) levanta los dos workers (worker.py:24-39).

API ── start_workflow ──▶ cola platform │ ▼ ReviewCommitWorkflow id: {kind}-{project_id}-{sha}[-r{run}] (workflows/review_commit.py:22-31) │ execute_child_workflow ▼ ReviewChangeWorkflow id: review-{change_id}-r{run} (workflows/review_change.py:29-47) │ asyncio.gather (fan-out en paralelo, uno por agente) ├──▶ activity run_review(agent_1) ──▶ cola agents └──▶ activity run_review(agent_2) ──▶ cola agents │ ▼ cada activity: carga el Change → agent.review() → guarda Review + evento en Postgres

Qué pasa cuando algo falla

El agente lanza una excepciónLa activity la captura, guarda Review(status=failed, error) + evento review.failed y devuelve status=failed; no la relanza (workflows/activities.py:57-70). El workflow termina Completed.
Fallo de infraestructura (BD, red)Lo reintenta la RetryPolicy (3 intentos, idempotentes). Si se agotan, falla la activity, el hijo y el padre.
Agente desconocido / change inexistenteApplicationError(non_retryable=True) sin guardar review (workflows/activities.py:43-47, 53-54): rompe todo el workflow.

¿Qué agentes existen de verdad?

Solo el FakeAgent (adapters/agents/fake.py:7): devuelve siempre nota 7 y un único hallazgo nit con file="N/A" y line=0 (:29-39; la UI oculta esos dos valores y lo agrupa bajo «Sin archivo»), o lanza RuntimeError si se construye con should_fail=True (:26-27). El worker crea uno por cada nombre de AGENT_NAMES, por defecto agent_1,agent_2 (worker.py:30, config.py:28). No hay adaptador de Claude ni de Codex en el backend, aunque la interfaz diga «Claude y Codex».

Ejecución

No existe un servicio worker en docker-compose.yml: se levanta con just worker. Si no hay worker escuchando, los workflows quedan en espera y los changes en pending.

5 · Lectura: cómo se calcula lo que se muestra

review_status

Se calcula siempre sobre las reviews del run actual (domain/review_status.py:24-53):

CondiciónEstado
0 reviewspending
menos reviews que agentes esperadosrunning
todas completadascompleted
todas fallidasfailed
mezclapartial_failed

«Agentes esperados» es len(AGENT_NAMES) de la API. En el listado lo calcula SQL con una subconsulta LATERAL (adapters/persistence/change_repository.py:90-104, :194); en el detalle, Python (application/queries.py:100). Un test comprueba que ambos coinciden.

stale (diagnóstico)

Un change en pending o running con más de 1800 s desde su creación se marca stale (domain/review_status.py:65-72). No relanza nada ni se guarda: se calcula al leer. Mide desde la creación, no desde el inicio del run actual.

Eventos

GET /changes/{id}/events expone solo change.created, review.completed y review.failed, sin el error ni el payload crudo (application/queries.py:124-135).

CORS y trazabilidad

CORS solo se activa si ALLOWED_ORIGINS no está vacío, con orígenes explícitos (nunca *) y sin credenciales: la autenticación va en cabeceras, no en cookies. Métodos permitidos: GET, POST y DELETE; cabeceras permitidas: Content-Type, X-Ingest-Token y X-Request-ID; expuestas: X-Request-ID y Retry-After (entrypoints/api/app.py:50-60). X-Operator-Token no está permitida: raw-output no se puede llamar desde un navegador. Cada respuesta lleva un X-Request-ID y se escribe una línea JSON de acceso, sin cuerpo, query ni tokens.

6 · Frontend: cómo se muestra

  • Fuente de datos. Con VITE_API_URL definida habla con la API por HTTP; sin ella usa datos de ejemplo (frontend/src/data/source.tsx:127). Un navegador sin variable no toca el backend.
  • Rutas (frontend/src/App.tsx:59-62): / redirige al primer proyecto; /p/* se interpreta a mano porque el slug owner/repo contiene una barra (canal en /p/owner/repo, detalle en /p/owner/repo/changes/{id}); /stats; /settings; cualquier otra ruta muestra «No encontrado».
  • Auto-actualización. Un sondeo cada 5 s (frontend/src/lib/polling.tsx:4) refresca la barra lateral, el canal y el detalle; se pausa con la pestaña oculta y el detalle solo sondea mientras la review está pending o running (frontend/src/features/review/ChangeDetailPage.tsx:24). No hay SSE ni WebSocket: ver un cambio «en tiempo real» significa «con hasta 5 s de retraso».
  • Canal. Búsqueda con debounce de 300 ms, filtros por tipo y estado en el servidor, «Cargar más» con el cursor, vista de tarjetas o compacta y antigüedad relativa.
  • Detalle. Diff numerado con navegador de archivos, panel de hallazgos agrupado por archivo (los que no traen archivo van en «Sin archivo»), una tarjeta por review con run, duración, nota y el error sanitizado.
  • Reintento. El botón aparece solo con failed o partial_failed y pide el token en un campo de contraseña que vive solo en memoria (frontend/src/features/review/RetryReview.tsx:71; nunca en localStorage, URL ni build).
  • Ajustes. Proyectos, diagnóstico de Postgres y Temporal con latencia, añadir proyecto local (ruta absoluta → instala hooks), sincronizar PRs con gh (application/local_projects.py:94-126, adapters/github/gh_cli.py:20-37) y quitar proyecto (borra su historial y exige que los hooks se hayan desinstalado).

7 · El reintento (run + 1)

  1. Comprobación. Solo se reintenta si el estado del run actual es failed o partial_failed (application/retry_review.py:42-49, domain/review_status.py:58); si no, 409. Un pending o running no se puede reintentar.
  2. Primero se arranca, después se avanza. Se arranca el workflow del run siguiente (application/retry_review.py:51) con id …-r2 y su hijo review-{id}-r2. Si el arranque falla (503), run no cambia y se puede repetir.
  3. Compare-and-swap. UPDATE changes SET run = run + 1 WHERE id = … AND run = 1 (adapters/persistence/change_repository.py:178-191): dos reintentos simultáneos arrancan una sola ejecución (mismo id de workflow) y solo uno avanza run.
  4. Se reejecutan todos los agentes del run nuevo, no solo el que falló. Las reviews del run anterior se conservan (la clave es (change, agent, run)), pero review_status y findings_summary solo cuentan el run actual.

8 · Lo que hay que saber: limitaciones reales

Todo lo siguiente se comprobó contra el código. Son decisiones o huecos conocidos, no promesas.

Orquestación

Heartbeat declarado, nunca enviado

heartbeat_timeout=30 s está en workflows/review_change.py:42, pero ninguna activity llama a activity.heartbeat(). Con un agente real que tarde más de 30 s, Temporal daría timeout y reintentaría sin motivo. Con el FakeAgent instantáneo no se nota.

Solo existe el FakeAgent

Sin adaptadores de Claude o Codex; el worker no está en docker-compose.yml; la lista de agentes debe coincidir entre la API y el worker o el estado se calcula mal.

Un fallo del agente no falla el workflow

Se guarda como Review(failed) y el workflow termina Completed; por eso ALLOW_DUPLICATE_FAILED_ONLY no lo relanza al reenviar el commit y hace falta el reintento (-r{run}).

Sin versionado de workflows, cancelación ni señales

No hay workflow.patched, continue_as_new, señales ni consultas. Cambiar el código de un workflow con ejecuciones en vuelo no está protegido contra no determinismo.

Ventana entre guardar y arrancar

Si la API muere entre guardar el change y arrancar Temporal, queda pending sin workflow. Solo lo señala stale; un pending no se puede reintentar (409) — la salida es reenviar el commit, que es idempotente.

raw_output siempre nulo

La activity guarda raw_output=None (workflows/activities.py:80), así que /reviews/{id}/raw-output da 404 para toda review creada por el flujo actual. El endpoint funcionaría (200 con token de operador) si algo guardara salida cruda.

El evento review.failed guarda el error

La API no lo expone, pero está en la tabla events; puede contener texto interno del agente.

API y datos

Reingestar no actualiza

Mismo (proyecto, kind, sha): 202 con created=false y se ignora el resto de campos (título, diff…).

Sin límite de cuerpo HTTP

diff no tiene max_length en el esquema: se recibe entero antes de truncar a 200 000 caracteres. title y author se truncan en silencio a 500 y 255.

Límite de peticiones en memoria

Por proceso y por IP del par TCP: con varios workers de uvicorn se multiplica, y detrás de un proxy sin --proxy-headers todos comparten IP. Solo cubre POST /ingest/*, el reintento y los endpoints de proyectos locales.

Lecturas sin autenticación

Los GET no piden token. Antes de exponer la API fuera de 127.0.0.1 hace falta autenticación de lectura. El INGEST_TOKEN es único y compartido (ingesta, reintento y proyectos locales).

Proyectos locales escriben en .git/hooks

Quien tenga el token hace que la API escriba código que se ejecuta en cada commit. Por eso está apagado por defecto, no es para contenedores ni servidores compartidos y los hooks son desinstalables.

Estadísticas y stale

/stats/agents cuenta las reviews de todos los runs. stale se mide desde created_at: tras un reintento sobre un change antiguo puede salir stale enseguida.

Frontend

El detalle mezcla runs

Muestra todas las reviews, sin filtrar por run (frontend/src/features/review/ChangeDetailPage.tsx:51), mientras el backend solo cuenta el run actual. Cada tarjeta indica su Run N.

Textos y constantes fijas

«Claude y Codex» está escrito a mano (frontend/src/features/channel/ChannelPage.tsx:172, frontend/src/features/settings/SettingsPage.tsx:60) y los agentes esperados valen 2 (frontend/src/lib/reviewStatus.ts:4), aunque el backend los configura.

El listado no trae reviews

Con la API real, «Ver respuestas» en el canal no tiene reviews que mostrar; el detalle sí las trae.
